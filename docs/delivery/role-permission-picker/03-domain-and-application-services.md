## The query a picker starts from

```dart
/// The query a **role's permission picker** starts from: the role's owner and scope, first page, the
/// resource's own (catalogue-first) order.
///
/// The two are *seeded*, not offered: every row this query returns is one the backend will accept for that
/// role (`RoleService.grantPermissions` filters by the same owner); a row outside them would be refused on
/// save with "Unknown permission" or "Permission scope mismatch". The picker therefore exposes search, the
/// owner filter (where more than one owner is grantable) and sorting — never a scope filter.
factory ListQuery.permissionsFor({String? ownerId, required String scope}) =>
    ListQuery(tenantId: ownerId, scope: scope);
```

`ownerId` is the role's owner — `null` for a global role on the platform plane, the chosen tenant's id for a
tenant-owned role. On the **tenant** plane it is passed as `null` and the tenant is dropped by
`ConsoleScope.permissions(query)` anyway, because the tenant route has no tenant parameter to name.

## The selection

```dart
@immutable
final class PermissionSelection {
  const PermissionSelection([Map<String, Permission> byCode = const <String, Permission>{}]);

  static const PermissionSelection empty = PermissionSelection();

  /// Toggles one row. The **row** is kept, not just the code: an owner/scope change has to be able to ask
  /// what each pick's owner and scope are without another request.
  PermissionSelection toggle(Permission permission, bool selected);

  /// The picks that survive [ownerId] + [scope], with the codes that did **not** — what the dialog says out
  /// loud instead of silently keeping a pair the backend would reject.
  ({PermissionSelection selection, List<String> dropped}) retaining({
    required String? ownerId,
    required String scope,
  });

  /// The chosen permissions, ordered by code, for display; [codes] feeds the request.
  List<Permission> get permissions;
  List<String> get codes;

  bool get isEmpty;
  int get length;
  bool contains(String code);
}
```

Rules it encodes (each unit-tested in phase 7):

1. **Keyed by code** — a code picked on page 1 is still picked after a search, a page change or a reopened
   picker; two rows never collapse into one, because `code` is what a role grant stores.
2. **`retaining`** keeps a pick when the new owner is `null` (every owner is grantable), when the pick is
   global (`tenant_id IS NULL` — grantable to every owner) or when its owner equals the new `ownerId`; and
   when its `scope` equals the new `scope`. This is `RoleService.grantPermissions`' two conditions, evaluated
   before the request instead of by it.
3. **Deterministic output** — `codes` is sorted, so the request body (and the created role's row) does not
   depend on the order the user clicked.

## The grantability mirror

```dart
/// Whether the caller may grant [code] to a role — the client mirror of `CallerScope.requireGrantable`
/// (`docs/ARCHITECTURE.md` §9.5 "grant only what you hold"). The **platform plane is unrestricted**, a
/// tenant caller may not grant the wildcard and may not grant a code it does not hold, and "holds" follows
/// the guard's implication: a read/write grant covers the read-only code of the same resource.
///
/// UX, not security: the backend refuses what this predicts, and the console must never be the only thing
/// standing between a tenant admin and an escalation.
bool canGrant(String code);
```

Implemented exactly like the backend (`CallerScope.requireGrantable` + its `holds`), so the picker's disabled
rows and the server's refusals agree; used **only to disable a row with a reason** (open question 3), never to
hide one.

**Deviations from the design, and why**

1. **The selection stores `PermissionPick` records (`code`, `scope`, `tenantId`), not `Permission` rows.** An
   edit starts from a `Role`, which carries its grants as **codes**, and the pruning rule needs only those two
   facts — so `PermissionSelection.ofRole(role)` can seed an edit without inventing a `Permission` row with a
   made-up id, and without a second request to resolve the codes. `PermissionSelection.of(Iterable<Permission>)`
   remains for the picker's own toggles.
2. **`isSeededAdminRole(Role)` is a function in `core/permissions.dart`, not a `Role.isSeededAdmin` getter.**
   A getter would make `models/models.dart` import the catalog, while the catalog already imports the models —
   a needless cycle. The catalog rule lives with the rest of the catalog knowledge instead.
3. **`ListQuery.permissionsFor` is a named factory on `ListQuery`** rather than a free function, so it sits
   beside `initial` and reads as what it is: a query, with the same value equality the provider family key needs.
4. **`UpdateRoleRequest` carries no `tenantId`** even though the backend's `RoleRequest` does: `RoleService.update`
   ignores it entirely (the owner is immutable), and a field that must never be sent is better absent than
   documented as "do not touch".
