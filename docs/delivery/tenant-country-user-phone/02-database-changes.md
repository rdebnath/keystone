# Phase 2 — Database changes

## Scope

Two nullable columns, added by one Liquibase changelog included from the master changelog. jOOQ
types are generated offline from the changelog (`DDLDatabase`), so the codegen reruns as part of the
build — the schema is never auto-generated from a live database.

## Artifacts

| Artifact | Change |
| --- | --- |
| `platform/keystone-admin/src/main/resources/admin-db/changelog/0004-tenant-country-user-phone.xml` | new — one changeset per column |
| `platform/keystone-admin/src/main/resources/admin-db/changelog/db.changelog-master.xml` | add the `0004` include |
| generated `…platform.admin.jooq.platform.tables.records.TenantsRecord` / `UsersRecord` | regenerated by the build (`target/generated-sources/jooq`) |

## Changesets

1. `0004-tenant-country` — `tenants.country VARCHAR(2)`, nullable.
2. `0004-user-phone` — `users.phone_number VARCHAR(32)`, nullable.

Both carry the `preConditions onFail="MARK_RAN"` / `columnExists` guard the earlier changelogs use,
so a database that already carries the column (an externally initialized schema) is left alone
rather than failing the migration.

No `NOT NULL` constraint, no default value and no backfill: the columns are optional business
metadata, so every existing row is already valid. Existing tenants/users simply report `null` until
someone records the value.

## Dependencies

- None. This is the first phase with artifacts.

## Execution (2026-09-28)

Created `0004-tenant-country-user-phone.xml` with the two changesets, added the master-changelog
include, and compiled with `mvn -pl platform/keystone-admin -am -DskipTests compile`. jOOQ reported
*"Affected files: 17, Modified files: 4"* and the rendered DDL (`target/generated-ddl/schema.sql`)
carries exactly:

```
-- Changeset .../0004-tenant-country-user-phone.xml::0004-tenant-country::keystone
ALTER TABLE platform.tenants ADD country VARCHAR(2);
-- Changeset .../0004-tenant-country-user-phone.xml::0004-user-phone::keystone
ALTER TABLE platform.users ADD phone_number VARCHAR(32);
```

so the offline `DDLDatabase` renderer accepts the DDL and the generated `TenantsRecord` /
`UsersRecord` (and the `Tables` constants) carry the fields — `TENANTS.COUNTRY` and
`USERS.PHONE_NUMBER` compile in the services. `TenantUserProfileSchemaTest` then asserts the columns,
their nullability and their lengths against PostgreSQL 17.

No deviation.
